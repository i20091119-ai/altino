## 0. 먼저 볼 것 (결론 4가지)

1. **`ALTINO-B7CE` 는 새온의 규칙으로는 라이트가 아니다.** [확인] 오케스트라2는 이름에 `ALTINO-L` 이 있으면 라이트, `ALTINO-N` 이 있으면 올뉴 알티노(우리가 '네오'라 부르던 것), 그 밖의 `ALTINO…` 는 **구형 알티노**로 분류한다. 구형 알티노는 보냄 28바이트 / 받음 56바이트로, 우리 앱이 보내 본 26바이트·22바이트와 전혀 다른 형식이다. 실기에서 두 형식 모두 답이 0이었던 것과 맞는다. → **앱에 세 번째 기종(구형 알티노 28/56)을 넣는 것이 다음 작업이다.** (5장)
2. **라이트 22바이트 프레임 자체는 우리 앱이 보내던 것과 같다.** [확인] 정지 상태 프레임 `02 10 02 01 01 00…00 03` 이 PC판과 바이트 단위로 일치한다. 진짜 라이트(`ALTINO-L…`)에는 지금 프레임이 통할 가능성이 높다. [미확인]
3. **"센서 요청 프레임 `[4]=0x03`" 은 틀린 추정이었다.** [확인] `[3][4]` 는 16비트 명령 번호다. `0x0101` = 출력 설정(답으로 센서 값이 온다), `0x0103` = **조향 설정값 읽기**. 센서 요청은 따로 없고 출력 프레임을 보내면 센서 프레임이 답으로 온다. → `protocol.js buildLiteRequest`, `kit.js` 의 끼워 보내기, 점검 화면 '센서 요청' 단추를 **지운다.**
4. **음수 인코딩이 2의 보수가 아니다.** [확인] 라이트·올뉴의 조향 음수는 `~|v|`(1의 보수)다. 우리 `protocol.js` 는 조향을 `v & 0xFF`(2의 보수)로 보내 1만큼 어긋난다. 모터는 이미 1의 보수로 맞다.

## 3. 알티노 라이트 — 프레임 [확인] `AltinoLite.cs`

### 3.1 공통 틀 (`SendUartMessageFrame`, BINARY)

`02 | 데이터 길이 | 체크섬 | 명령 hi | 명령 lo | 데이터… | 03`

- 체크섬 = 명령 2바이트 + 데이터의 합 `& 0xFF` (라이트면 `frame[3..20]`. STX·길이·체크섬·ETX 는 빼고 더한다).
- 라이트의 데이터는 항상 16바이트 → 전체 22바이트. 아래에서 `d[n]` = 데이터 n번째 = 프레임 `[5+n]`.

### 3.2 명령 번호 (`UART_MSG_ID`)

| 번호 | 이름 | 쓰임 |
|---|---|---|
| `0x0101` | SET_OUTPUT_FUNCTIONS | 출력 설정. **답으로 센서 프레임(`0x0101`)이 온다.** 주기적으로 계속 보내는 것이 이것 |
| `0x0102` | SET_STEERING_PARAMS | 조향 설정값 쓰기 |
| `0x0103` | GET_STEERING_PARAMS | 조향 설정값 읽기 |
| `0x0104` | SET_SYSTEM_PARAMS | 기기 정보 쓰기 |
| `0x0105` | GET_SYSTEM_PARAMS | 기기 정보(펌웨어·하드웨어 버전, 제조번호) 읽기 |
| `0x0106` | SET_IR_TUNNING | IR 센서 초기화(PC 화면 이름 'SetIRReset') |
| `0x0107` | SET_PARAMS_FLASH_WRITE | 설정값을 플래시에 저장 |
| `0x0108` | SET_IR_OUTPUT | 상수만 있고 쓰는 곳 없음 |
| `0x8080` | JUMP_TO_BOOTLOADER | 부트로더 진입 |
| `0x0201` | ERROR | 로봇이 보내는 오류 답 |

### 3.3 출력 프레임 `0x0101` 의 데이터 16바이트

| 데이터 | 프레임 | 내용 | 인코딩 |
|---:|---:|---|---|
| d[0] | [5] | 조향 | 오른쪽 = 값 그대로(1~127), 왼쪽 = `~값`, 가운데 = 0 |
| d[1],d[2] | [6],[7] | 구동 A | 0~1000, hi·lo. 음수면 hi·lo 각각 `~` |
| d[3],d[4] | [8],[9] | 구동 B | 같음 |
| d[5] | [10] | 표시 방식 | `0xFF` = 점 그림, 그 밖 = ASCII 글자 코드(펌웨어가 글자를 그림) |
| d[6]~d[13] | [11]~[18] | 점 그림 8줄 | 3.4 참고 |
| d[14] | [19] | 소리 | 0 = 끔, `(옥타브-1)*12 + 음` (음: 도=1 … 시=12) |
| d[15] | [20] | 불빛 | 비트0 전조등(1) · 비트1 브레이크(2) · 비트2 왼쪽 깜빡이(4) · 비트3 오른쪽 깜빡이(8) |

- 구동 A·B 의 좌우: 스크래치 블록 `go left:[LEFT] right:[RIGHT]` → 메시지 `SetDrivePwr:LEFT:RIGHT` → 코드가 `SetDrivePwr(array[2], array[1])` 로 뒤집어 받아 **RIGHT 값이 d[1..2], LEFT 값이 d[3..4]** 로 간다. 실제 바퀴와의 대응은 [미확인].
- 구동 값이 1000 을 넘으면 1000 으로 자른다. 조향은 ±127 로 자른다.
- 조향 블록 `Left-5/10/15/20`, `Right-5/…` 는 숫자 × 6.35 를 정수로(20 → 127).
- 소리 예: 4옥타브 도 = 37, 레 39, 미 41, 파 42, 솔 44, 라 46, 시 48, 5옥타브 도 49 — 우리 앱이 쓰던 값과 같다.
- 불빛: **라이트의 전조등은 1** 이다. 우리 앱 기본값 `ledMask 15` 는 올뉴 알티노 기준(전조등 1|2 + 후진등 4|8)이라 라이트에서는 네 등이 다 켜진다.

### 3.4 점 그림

- `d[5] = 0xFF` 로 두고 8바이트를 채운다. PC 코드의 여러 함수가 모두 `d[13 - i]` 에 i번째 값을 넣는다.
  - `SetDisplayHex(값1..값8)`: 값 i(0부터) → `d[13-i]` → 프레임 `[18-i]`.
  - `SetDisplayMatrix(x, y, 켬/끔)`(1~8): `d[13-(x-1)]` 의 비트 `(y-1)`.
  - `SetDisplayLine(줄 n, 비트 8개)`: 줄 n 이 **비트 자리**(1줄=비트0 … 8줄=비트7), 8개 값이 **바이트 자리**(`d[13-i]`).
- 우리 `protocol.js` 의 `dot[8-col] |= 1<<(row-1)`, `frame[11+i] = dot[i]` 와 같은 배치다(col↔x, row↔y). 실제 방향(어느 쪽이 위·왼쪽)은 [미확인].
- 글자 한 개: `d[5]` = ASCII 코드, `d[6..13]` = 0.
- 흐르는 글자(`SetDisplay 글자열, Speed-1~5`): PC가 8×8 글꼴 표(127자, `dt_font_arry`)에서 한 글자당 8바이트를 꺼내 **비트 순서를 뒤집어** 이어 붙이고, 한 칸씩 밀면서 `d[13-j]` 에 넣는다. 한 칸 미는 간격 = Speed-1 500ms, -2 400ms, -3 300ms, -4 200ms, -5 100ms. 글자열 앞에 공백 한 칸을 붙인다. ASCII 127 초과 글자는 거부.
- 지우기: 스크래치 '정지'는 `SetDisplayChar:' '`(공백 글자)를 보낸다.

### 3.5 받는 프레임 (22바이트)

- 정확히 22바이트를 모아 `[0] == 0x02` 만 확인한다. **받는 쪽 체크섬은 검사하지 않는다**(검사 함수 `isChecksumResGood` 는 있으나 호출하지 않음).
- `[3][4]` = 답의 명령 번호, `[5..20]` = 데이터 16바이트.

`0x0101` 답(센서):

| 데이터 | 프레임 | 값 |
|---|---|---|
| d[0,1] ~ d[10,11] | [5,6] ~ [15,16] | IR-1 ~ IR-6 (16비트, hi 먼저, 부호 없음) |
| d[12,13] | [17,18] | CDS(조도). 화면 단위 표기 'lx' |
| d[14,15] | [19,20] | 배터리 원값. 화면 값 = `round(원값 × 1.17)`, 100 초과는 100 (단위 %) |

- IR 값이 가까울수록 커지는지, IR-1~6 의 위치는 코드에 없다. [미확인]

### 3.6 보내는 주기 (`SensorRequestTaskAction`)

1. 출력 프레임을 보낸다(보내기 전에 받는·보내는 버퍼를 비운다).
2. 답(`0x0101`)이 올 때까지 기다린다. 1000ms 넘으면 버퍼를 비우고 포기.
3. 10ms 쉬고 1번으로.

- 즉 **답을 받은 뒤 다음 프레임을 보내는 주고받기 방식**이다. 답이 빠르면 초당 수십 번 돈다. 우리 앱은 답과 상관없이 10Hz 로 보낸다 — 문제는 없어 보이나 [미확인].
- 스크래치 → PC 는 30ms 마다 바뀐 명령만 모아 보낸다(4.6).
- 직렬 포트 속도 115200. 받는 문턱 22바이트, 쓰기 제한 1000ms.

### 3.7 관리용 명령

공통 절차: 주기 전송을 멈춤 → 500ms 대기 → 명령 프레임 1번 → 같은 명령 번호의 답을 최대 약 2초 기다림 → 주기 전송 재개.

| 명령 | 보내는 데이터 | 답 |
|---|---|---|
| `0x0105` 기기 정보 읽기 | 0 × 16 | d[0] = 하드웨어 버전(16진 2자리로 표시), d[1..4] = 제조번호(32비트, 16진 8자리), d[5..6] = 펌웨어 버전(정수, 예 1008) |
| `0x0103` 조향 설정 읽기 | 0 × 16 | d[0] = 부호 있는 값(음수면 +1 해서 표시 = 1의 보수 풀기), d[1], d[2], d[3] |
| `0x0102` 조향 설정 쓰기 | d[0..3] = 값 4개, 나머지 0 | 같은 4개 값 |
| `0x0106` IR 초기화 | 0 × 16 | 답이 오면 완료 |
| `0x0107` 플래시 저장 | 0 × 16 | 답이 오면 완료 |
| `0x0104` 기기 정보 쓰기 | 16진 문자열 3개를 이어 5바이트 + 0 × 11 | 답이 오면 완료 |

- 조향 설정 4개 값의 뜻은 라이트 코드에 이름이 없다. 구형 알티노 코드의 같은 자리 변수 이름이 trim·pGain·iGain·dGain 이다. [추정]
- 기기 정보 쓰기의 5바이트 구성(하드웨어 버전 1 + 제조번호 4 로 보임)은 [추정]. 앱에서 쓸 일 없음.
- PC는 연결 뒤 `VersionCheck`(= `0x0105`)를 보내 펌웨어 버전을 `version.json` 의 목표값과 비교하고, 낮으면 업데이트를 권한다.

### 3.8 부트로더(펌웨어 올리기) — 참고용, 앱에서 건드리지 말 것

- 글자 프레임: `'/'` + 명령 2글자 + 데이터 8바이트를 16진 글자 16개로 + 체크섬 16진 2글자 + `'\n'` = 22바이트. 체크섬 = `'/'` 다음부터 데이터 끝까지 글자 코드 합 `& 0xFF`.
- 순서: `SO`(데이터 `…01`) → 답이 `BS` 가 아니면 바이너리 `0x8080` 으로 부트로더 진입 → `EF`(지우기: `08 00 80 00` + 크기 4바이트, 2048 단위 올림) → `SF`(쓰기 시작: 같은 주소 + 크기) → `SD`(8바이트씩, 4바이트 단위로 바이트 순서 뒤집음) 반복, 답 `SD`/끝나면 `SE` → `RF` 로 되읽어 비교 → `JP`(`08 00 E0 00 …`, 앱 시작 주소로 점프).
- 주소: 플래시 시작 `0x08008000`, 앱 주소 상수 `0x0800E000`. hex 파일 범위 `0x08008000~0x0801F7FF`(96,256바이트), 초기 스택 `0x20004000`.
- 라이트와 올뉴 알티노의 hex 는 크기가 같고 내용은 다르다.

## 4. 알티노 라이트 — PC판 안쪽 구조 [확인]

### 4.1 연결 경로

- 로봇과의 연결은 전부 **직렬 포트**로 추상화돼 있다. 두 가지: ① S-Link 동글(USB, CP210x 드라이버 + RN4678 모듈) ② PC 블루투스 클래식(가상 COM 포트).
- 동글 제어(RN4678 명령): `$$$`(설정 모드, 답 `CMD>`), `SM,0`/`SM,6`(모드, 6 = 자동 연결), `F`(스캔 — 답은 `%주소,이름%` 줄, 끝 `%END_INQ%`), `C,<주소>`(연결, 답 `%RFCOMM_OPEN%`/`%BONDED%`), `K,1`(끊기), `R,1`(재시작), `GM`/`GK`/`GR`(모드·상태·상대 주소 조회), `---`(설정 모드 나가기).
- PC판은 BLE GATT 를 직접 다루지 않는다. GATT UUID·MTU·쓰기 방식에 관한 정보는 PC판에 없다.

### 4.2 명령 문자열 (`AltinoLite.SendMessage`)

`SetDrivePwr:L:R` · `SetSteeringByte:n` · `SetSteering:Center|Left-n|Right-n` · `IndicatorLedHex:값` · `IndicatorLed:Forward|Brake|Turn Left|Turn Right:On|Off` · `SetBuzzerByte:n` · `SetBuzzer:n-Oct:음이름` · `SetDisplayChar:c` · `SetDisplayLine:Line-n:On|Off×8` · `SetDisplayHex:값×8`(`0x..`, `0b..`, 10진 가능) · `SetDisplayMatrixOn:x:y` · `SetDisplayMatrixOff:x:y` · `SetDisplay:글자열:Speed-n` · `RequestSensorValue` · `VersionCheck` · `RefreshDeviceInfo` · `RefreshSteeringParam` · `SetParamSteering:a:b:c:d` · `SetIRSensorInit` · `WriteParamToFlash` · `WriteDeviceInfo:a:b:c` · `UpgradeFirmware:경로`

- 문자열 비교가 `Contains` 순서대로라 `SetSteeringByte` 가 `SetSteering` 보다, `IndicatorLedHex` 가 `IndicatorLed` 보다 먼저 걸린다.
- 이 명령들은 주기 프레임의 데이터만 바꾼다. 실제 전송은 3.6 의 주기 루프가 한다(우리 kit 구조와 같다).

### 4.3 알림 문자열

`[AltinoLite][Sensor][ALL][CDS:IR1:IR2:IR3:IR4:IR5:IR6:BAT]` · `[AltinoLite][Version][INFO][FIRMWARE|HARDWARE|SERIALNO][값]` · `[AltinoLite][Version][INFO][UNKNOWN]` · `[AltinoLite][Admin][READ][SteeringParam:a:b:c:d]` · `[AltinoLite][Admin][READ][SetSteeringParam:…]` · `[AltinoLite][Admin][READ][SetIRReset][Done|Fail]` · `[AltinoLite][Admin][INFO][WriteParam][Done|Fail]` · `[AltinoLite][Connection][Unstable]`(1초 무응답 뒤 버퍼 비우기 실패 때) · `[AltinoLite][Flash][INFO|ERR][…]`

### 4.4 센서 이름·순서

`CDS, IR-1, IR-2, IR-3, IR-4, IR-5, IR-6, BAT` — `GetSensorValues()` 가 이 순서로 `:` 로 이어 돌려준다.

## 5. 구형 알티노 (`ALTINO-xxxx`) — `ALTINO-B7CE` 가 여기에 해당 [확인] `Altino.cs`

### 5.1 보내는 프레임 28바이트 (주기 프레임 `byArrDataReqFrame`)

기본값: `02 1C cc 00 0A 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 0A 00 00 01 00 00 03`

| 프레임 | 내용 | 인코딩 |
|---:|---|---|
| [0] | `0x02` | |
| [1] | `0x1C`(28, 전체 길이) | |
| [2] | 체크섬 | `[1]~[27]` 중 `[2]` 를 뺀 합의 아래 8비트 (**ETX 포함, STX 제외**) |
| [3] | `0x00` | 주기 프레임. 관리 프레임은 `0x01` |
| [4] | `0x0A` | 고정값(뜻 불명). 관리 프레임은 `0xFF`(버전)·`0xFC`(조향 설정) |
| [5] | 조향 | 오른쪽 = 값, 왼쪽 = `값 \| 0x80`, 가운데 = 0. 블록 `Left-n` 은 n × 6 (최대 128) |
| [6] | 0 | |
| [7],[8] | 구동 A hi·lo | 0~1000. 음수면 **hi 에만** `\| 0x80` |
| [9] | 0 | |
| [10],[11] | 구동 B hi·lo | 같음 |
| [12] | 표시 방식 | 0 = 점 그림, `글자 코드 \| 0x80` = 글자 |
| [13]~[20] | 점 그림 8줄 | i번째 값 → `[20-i]`. `SetDisplayMatrix(x,y)` → `[20-(x-1)]` 의 비트 `(y-1)` |
| [21] | 아래 4비트 = `0xA` 고정(뜻 불명), 위 4비트 = 불빛 | 브레이크등 = `0x80 \| 0x40` |
| [22] | 소리 | 라이트와 같은 식 `(옥타브-1)*12 + 음` |
| [23] | 불빛 | 전조등 `1\|2` · 후진등 `4\|8` · 오른쪽 깜빡이 `0x10\|0x40` · 왼쪽 깜빡이 `0x20\|0x80` |
| [24] | `0x01` | 조향 보정 사용 표시로 보임 [추정] |
| [25] | 조향 보정값 | 음수면 `\|값\| + 128` |
| [26] | 0 | |
| [27] | `0x03` | |

- 구동 A·B 의 좌우는 라이트와 같은 뒤집힘: 스크래치 RIGHT → `[7,8]`, LEFT → `[10,11]`.
- 구동 값이 1000 을 넘으면 그 명령을 **무시**한다(라이트는 자름).
- `[4]=0x0A`, `[21]` 아래 4비트 `0xA` 의 뜻은 코드에 없다. 기본값 그대로 보낼 것.

### 5.2 받는 프레임 56바이트

- 정확히 56바이트를 읽는다. 체크섬 검사: **`[0]~[55]` 중 `[2]` 를 뺀 합 == `[2]`**(보낼 때와 달리 STX 포함). 우리 쪽은 두 방식 모두 허용하도록 느슨하게 받을 것. [미확인]

| 프레임 | 값 |
|---|---|
| [7,8] ~ [17,18] | IR-1 ~ IR-6 (16비트, hi 먼저) |
| [19,20] / [21,22] / [23,24] | 모터 전류 왼·오른 / 조향 전류 |
| [25,26] [27,28] [29,30] | 가속도 X·Y·Z (부호 있는 16비트를 4비트 오른쪽으로 민 값) |
| [31,32] [33,34] [35,36] | 지자기 X·Y·Z (부호 있는 16비트) |
| [37,38] [39,40] [41,42] | 자이로 X·Y·Z |
| [43,44] | CDS |
| [47,48] | 배터리 ADC. 전압 = `0.0027 × 값 + 5.8958`, 7.0V 이하 0%, 8.3V 이상 100%, 사이는 직선 |
| [49,50] | 온도 ADC (4차 다항식 변환) |

### 5.3 주기

보냄 → 30ms 쉼 → 56바이트 답 대기(기본 제한 1000ms, 넘으면 버퍼 비우고 다시 보냄) → 답이 오면 바로 다음. 직렬 115200.

### 5.4 관리 프레임

- 버전 요청: 28바이트 `02 1C 1F 01 FF 00…00 03` → 답 **31바이트**, 버전 글자 5개가 `[15..19]`.
- 조향 설정 읽기: 22바이트 `02 16 cc 01 FC 00 00…03` → 답 31바이트, 값 4개가 `[5..8]`.
- 조향 설정 쓰기: 22바이트 `02 16 cc 01 FC 01 trim p i d … [17]=버전 … 03` → 답 31바이트.
- 체크섬 규칙은 5.1 과 같다.

## 6. 올뉴 알티노(`ALTINO-N…`) — 우리 '네오' 와 대조 [확인] `AllNewAltino.cs`

- 보냄 26바이트(명령 `0x0101`, 데이터 20), 받음 54바이트 — 우리 `protocol.js` 의 네오 프레임·센서 자리(조도 `[47,48]`, 배터리 `[49,50]`)와 일치한다.
- 받는 데이터(프레임 = 5 + 자리): ToF-1~6 `d[0..11]`, 가속도 `d[12..17]`, 지자기 `d[18..23]`, 자이로 `d[24..29]`, AHRS roll·pitch·yaw `d[30..35]`, 온도 `d[36,37]`, 모터 전류 좌·우 `d[38..41]`, CDS `d[42,43]`, 배터리 `d[44,45]`(× 1.17, 최대 100). 값은 부호 있는 16비트.
- 불빛: `d[15]`(프레임 [20]) 브레이크 `1|2`, `d[16]`(프레임 [21]) 전조등 `1|2` · 후진등 `4|8` · 오른쪽 깜빡이 `0x10|0x40` · 왼쪽 깜빡이 `0x20|0x80`. → 우리 앱의 `ledMask 15` = 전조등 + 후진등.
- 조향·구동·점 그림·소리 자리는 라이트와 같다(`d[0]`, `d[1..4]`, `d[5..13]`, `d[14]`).
- 명령 번호도 같고 `0x0106` 만 AHRS_CALIBRATION 이다.

## 7. 우리 앱에 반영할 일

우선순위 순.

1. **구형 알티노(28/56) 기종 추가** — `protocol.js` 에 `buildClassicFrame`·`parseClassicFrame`, `SensorFrameAssembler` 에 56바이트. 모델 이름은 `classic`.
2. **이름 규칙을 새온과 같게** — `ALTINO-L` → lite, `ALTINO-N` → neo, 그 밖의 `ALTINO`/`RN4678`/`RNBT` → classic. 지금은 'L 이 아니면 네오'라서 구형을 네오로 본다. 기종 자동 찾기(`kit.js probeModel`)는 이름으로 고른 기종이 답이 없을 때 나머지 둘을 차례로 시도하도록 3종으로 넓힌다.
3. **센서 요청 프레임 삭제** — `buildLiteRequest`, `kit.js send` 의 끼워 보내기, 점검 화면 '센서 요청' 단추, `tests/probe.mjs` 의 `[4]=3` 가정. `0x0103` 은 조향 설정 읽기라서 계속 보내면 로봇이 센서 대신 설정값으로 답한다.
4. **조향 인코딩** — lite·neo: 음수는 `(~|v|) & 0xFF`. classic: `|v| | 0x80`.
5. **모터 인코딩(classic)** — hi 바이트에만 부호 비트. lite·neo 는 지금대로.
6. **불빛 값을 기종별로** — 전조등: lite `1`, neo `[21]=3`, classic `[23]=3`. `Camp.settings.ledMask` 기본값 15 를 기종에 따라 정하거나, kit 에 뜻 이름(`forward`/`brake`/`left`/`right`)으로 켜는 함수를 둔다. t05·c03 이 이 값을 쓴다.
7. **배터리 표시** — lite·neo: `원값 × 1.17`(최대 100)이 %. classic: 5.2 의 전압식. 지금 화면의 '🔋 764' 같은 원값 표시와 `BATT_LOW` 기준을 기종별로 다시 잡는다.
8. **센서 이름** — neo 는 IR 이 아니라 ToF 다(단위·방향이 다를 수 있다). c04·t06 의 '가까우면 커진다' 가정은 기종별로 실측해야 한다.
9. **classic 받는 체크섬**은 STX 포함·제외 둘 다 허용.
10. 문서 고치기 — `CLAUDE.md` '확인된 사실'의 "이름이 ALTINO-L… 이면 라이트(그 밖은 네오)" 와 `HANDOFF.md` 3번의 센서 요청·ESP32 추정을 이 문서 내용으로 바꾼다. ESP32 추정은 근거가 약하다(구형 알티노 펌웨어가 RN4678 계열 명령을 쓴다).

## 9. 아직 모르는 것

- `ALTINO-B7CE` 가 실제로 구형 알티노 형식에 답하는지(가장 먼저 확인). 사용자가 이 로봇을 라이트로 알고 있는지, 겉모습이 어느 기종인지도 물어볼 것.
- 캠프에서 쓸 로봇의 이름이 `ALTINO-L…` 인지 — 새온에 확인. 캠프용이 진짜 라이트라면 지금 앱의 라이트 프레임이 그대로 통할 가능성이 높다.
- BLE 쪽 세부(쓰기를 한 번에 22/28바이트로 보내도 되는지, 응답 없는 쓰기로 되는지): PC판에는 정보가 없다. 실기 관찰로는 서비스 `49535343…` 하나에 알림(rn)·쓰기(wc) 특성 둘, 쓰기는 성공했다.
- 구동 A·B 와 실제 좌우 바퀴, 점 그림 방향, IR 번호별 위치와 값의 방향, 불빛 비트의 실제 등.
- 구형의 `[4]=0x0A`·`[21]` 아래 4비트·`[24]=1` 의 뜻.
- 안드로이드 오케스트라2가 PC판과 같은 이름 규칙·프레임을 쓰는지.
